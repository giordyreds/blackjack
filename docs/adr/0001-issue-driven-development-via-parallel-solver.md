# Issue-driven development via parallel-solver

We're building this game's features as separate GitHub issues (Card/Shoe model, Hand evaluation, Hit/Stand loop, Double/Split, Betting & bankroll, Dealer peek rule, CLI game loop), solved unattended by `parallel-issue-solver` rather than written by hand. Each issue runs in its own Docker sandbox and opens a PR for review; nothing auto-merges. Several issues depend on the Card/Shoe model landing first, so `dependencies.enabled: true` is set and those issues use GitHub's native "blocked by" links — parallel-solver stacks their branches on the blocker's branch instead of running them against a codebase that doesn't exist yet. Sandboxed commits are authored as `Blackjack Solver Bot <blackjack-solver@users.noreply.github.com>`, kept distinct from the maintainer's own commits.

We considered the `worktree` sandbox backend (rejected — runs unattended directly against the host filesystem, requiring an explicit risk acknowledgement for no real benefit here) and running dependent issues manually in separate sequential batches (rejected — the tool's dependency scheduling does this automatically once the blocking links exist).
